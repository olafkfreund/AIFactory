# Intent: run the target repo's lint as a trailing gate

Code paths are at commit 4638e87d (origin/dev, 2026-10-17).

## Problem

Follow-up to #1627 (PR #1743). That change only *records* a CI linter that
no gate ran: `ci_linters` (`apps/backend/analysis/ci_discovery.py:458`)
finds allowlisted linter names in the target repo's CI, and the trailing
gate run (`apps/backend/agents/coder.py:1353-1360`) appends
`<linter>: skipped`. Nothing runs the linter, so a build whose code breaks
the repo's lint still reports complete and the PR is the first place the
failure shows up (the MyFriends ktlint case: 240 violations after a
"complete" build).

Two gaps remain:

- **Planning never sees the repo's lint.** `generate_planner_prompt`
  (`apps/backend/prompts_pkg/prompt_generator.py:236`) gives the planner no
  hint which linters CI runs, so no subtask plans to keep them clean.
- **No lint gate runs.** `detect_gates`
  (`apps/backend/agents/gate_runner.py:100`) has only `npm run lint`.

Also open from the #1627 review (LOW): `ci_linters` parses every workflow
file in the repo, with no cap on the count.

## Proposed outcome

- When enabled, the planner prompt names the linters the target repo's CI
  runs, so the plan can keep them clean.
- When enabled, the trailing gate runs each detected linter it has a curated
  command for. A lint that ran and failed is a gate failure: it writes
  `GATE_FAILURES.md` and the QA/fix loop acts on it, the same as a failed
  test gate. A linter whose tool is missing stays `skipped`.
- Off by default: turning lint into a blocking gate can fail builds that
  pass today, so an operator opts in.
- `ci_linters` refuses a repo with an unreasonable number of workflow files.

## Affected users and systems

- Operators and reviewers of builds on repos with ktlint / ruff / flake8 in CI.
- The PARR chain: with the flag on, a lint failure goes to the QA fix loop
  instead of a red required check on the PR.
- Code: `analysis/ci_discovery.py`, `agents/gate_runner.py`,
  `agents/coder.py`, `prompts_pkg/prompt_generator.py`, the build Job env
  forwarding (`apps/web-server/server/services/build_backend.py:253`), and
  the env reference doc.

## Constraints

- Command text from the target repo's CI is untrusted and must never be run
  or reach a prompt or the evidence. Only allowlisted names and curated
  commands are used.
- Lint runs only through the existing gate runner (`run_gates`, sandbox
  `network=none` by default, `GATE_TIMEOUT_SECONDS`).
- The trailing-gate path never raises (`coder.py`, outer `try`).
- Completion banners are not reworded (Q7 of the issue: their consumers
  parse them); evidence keeps the `passed/failed/skipped` vocabulary that
  `gate_outcomes` (`gate_runner.py:900`) accepts.
- Default behaviour (flag unset) must stay byte-identical.

## Open questions

1. Should a lint that ran and failed block completion? Proposed: yes, when
   the operator enabled the flag (that is the point of enabling it).
2. Run lint through a new descriptor `lint` lane (issue Q3) or a curated
   per-linter table in `gate_runner`? The descriptor YAMLs and
   `KNOWN_LANES` are vendored from the Factory hub under a drift gate, so a
   new lane key is a cross-repo change. Proposed: the curated table now.
3. Provide the linter from nix and record its version (issue Q4)?
   Proposed: not now; a missing tool is `skipped`.
