# Intent: a `ci-green` system gate never clears, so no planned task auto-merges

## Problem

The E2E campaign (Factory#3882) builds a tiny Python CLI through the factory. The build passes,
the independent review passes, the PR opens and CI goes green, but AIFactory never merges it.

The 3.21.14 diagnostic log shows why:

```
auto-merge withheld, merge policy says hold-blocking
(reviewTier=auto; AIFACTORY_AUTO_MERGE is on but the policy is stricter)
```

The cause is in the RFC-0013 deployment overlay:

- PFactory's signed task contract declares `deployment.system_gates: ["ci-green"]` for any repo
  that has CI.
- `merge_policy.deployment_block_reasons` holds the merge for every required system gate that is
  not in `satisfied_gates`.
- Nothing in AIFactory ever passes `ci-green` as satisfied. Every `merge_disposition` call in
  `pr_endgame` passes either no gates or `HUMAN_ONLY_GATES` (`{"human-approval"}`, used only after
  the watcher has verified a real approval on the head).
- So `decide_merge` returns `hold-blocking` before it even looks at the tier.

The PR opens with `auto_merge=False`. The merge gate is then never built, and the watcher exits
with `auto_merge_disabled`. Arming auto-merge alone would not help: the merge-time call holds on
the same unsatisfied gate.

`ci-green` is a gate AIFactory already measures. Before a low tier merges, `decide_merge` requires
`host_ci_green`, which the merge gate builds from every check on the head SHA plus the base
branch's required checks, and which fails closed when no CI ran. So the gate duplicates a signal
we already check, yet it can never clear. (One difference: red CI alone gives `hold-async`, while
an unsatisfied `ci-green` escalates to `hold-blocking`.)

The same unsatisfied gate makes `apply_path_risk_floor` record `pathRiskFloor: blocking` for a
harmless 3-file diff. That is advisory on prod today, but for legacy tasks the floor is enforced
(#1697), and the PR body and audit trail report a "blocking" risk that does not exist.

Seen on prod: e2e runs `h`, `i` and `j` (2026-11-25/26), all on
`001-wordfreq-deterministic-word-fr`.

## Proposed outcome

- A low-tier task whose contract requires `ci-green` auto-merges once the host's required CI is
  green, the review approves and the other existing gates pass.
- It is still held while CI is red, pending or unreadable.
- Every other system gate (`human-approval`, `security-scan`, `sbom`, `dr-signoff`, unknown names)
  still holds until it has evidence, exactly as today.
- Before the PR exists, `apply_path_risk_floor` ignores `ci-green` only. Diff-based floors,
  contract holds, high-risk and production blocks, and every other required gate still raise the
  floor as today.
- Scope is PRs opened after the release. PRs already opened with auto-merge off (e2e runs `h`,
  `i`, `j`) stay as they are; the harness sweeper removes them.
- Live proof: E2E P1 reaches S4 (service merge) and S5 (TFactory verdict on the merge SHA), within
  the watcher's existing window.

## Affected users and systems

- AIFactory web server: `apps/web-server/server/services/pr_endgame.py` (`merge_disposition`,
  `apply_path_risk_floor`). Possibly `apps/backend/merge/merge_policy.py`.
- Every project whose PFactory contract declares `ci-green`, which today is every repo with CI.
- Prod AIFactory (release to `main`, ArgoCD deploy).

## Constraints

- The merge gate may only become less strict for `ci-green`, and only when host CI is measured
  green. No other gate gets looser.
- Gate evidence must come from a measurement AIFactory made (the host CI check), never from the
  contract, `task_metadata.json` or anything the agent wrote (#1663, #1672).
- Fail closed: unknown, missing or errored CI means `ci-green` is unsatisfied.
- Keep RFC-0013's rule that the overlay only tightens the tier decision.
- No change to PFactory's contract format.

## Open questions

1. Should `ci-green` be satisfied from the measured `host_ci_green` signal (proposed), or should
   PFactory stop emitting `ci-green`, since the tier rule already demands CI?
2. At PR-open time the endgame uses *prospective* signals (`host_ci_green: True`) to decide
   whether to arm auto-merge. Is it acceptable that `ci-green` counts as prospectively satisfied
   there, given the real merge gate re-checks measured CI before merging?
3. Is it acceptable that `apply_path_risk_floor`, which runs before any CI exists, ignores
   `ci-green` (and only `ci-green`), since the merge gate checks it against measured CI later?
