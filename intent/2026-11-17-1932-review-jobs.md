# Intent: PR review and clarification sessions as Jobs (slice A4, #1932)

## Problem

`pr_review_service.py` (reads attacker-controlled PR diff, title, body) and `clarification_service.py` (reads attacker-controlled issue text) spawn LLM agent CLIs inside the web-server pod as the server uid. Builds and spec creation already run as Jobs; these two do not.

## Proposed outcome

Behind a new default-off flag `AIFACTORY_REVIEW_BACKEND=kubejob`, a PR review and a clarification run as Kubernetes Jobs. Only allowlisted output returns to the control plane: the review result JSON for the PR, or the clarification JSON text. With the flag off, behaviour is unchanged.

## Affected users and systems

AIFactory web-server (`services/`), `runners/github/runner.py`, `core/workspace_fetch.py`. Needs the S3 artifact store and the Job substrate already used by spec creation.

## Constraints

Default off; the Job returns only capped output (review JSON, clarification text, and logs are size-limited before buffering); cancel and timeout delete the Job (SpecJobProcess terminate path); no new secret reaches the Job beyond what spec Jobs get (OAuth token, plus the GitHub token a review needs to read the PR). Job output is untrusted: validated, size-capped, written only to `review_{N}.json`. Do not touch the live cluster.

## Open questions

None. Decision (owner delegation 2026-11-17): reuse the spec Job substrate (`SpecJobProcess`) rather than build a second one; one flag for both sessions (`AIFACTORY_REVIEW_BACKEND`), because they share the same risk and failure handling.
