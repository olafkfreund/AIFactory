# Intent: Cap AIFactory's DB connection pools so the fleet fits the shared Postgres

## Problem

AIFactory's main SQLAlchemy engine uses library defaults (5 + 10 overflow = 15 per
pod), and the tenant-teardown CronJob (`server/services/tenant_teardown.py:159`) builds a second default engine. At current KEDA maxima the fleet
can open far more connections than the shared Postgres's 97 usable ones, so a
burst in one service can starve the others. A saturated pool waits 30 s.

## Proposed outcome

Every engine in AIFactory has an explicit, env-tunable cap and a 10 s pool timeout,
sized so the fleet worst case fits in 97 with headroom. SQLite dev unchanged.
Live use today is a few connections per pod, so behaviour does not change.

## Affected users and systems

AIFactory web-server pods (and the daily tenant-teardown CronJob) on the shared k3d Postgres; PFactory and
KEDA indirectly. Companion of PFactory#964 (PFactory#961).

## Constraints

No gitops or cluster change, no deploy.
