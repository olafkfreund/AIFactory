# Intent: Scope each agent Job's S3 access to its own task

## Problem

Build Jobs and the spec Job (#1932) receive the control plane's `S3_ACCESS_KEY` /
`S3_SECRET_KEY` through `build_backend.build_job_env`. Those are the MinIO root
keys (factory-gitops `apps/minio`: `minio-creds` is the root user). A hostile
agent in one Job can list the bucket, read another task's packed workspace and
overwrite another task's fetch-back objects (`spec/<name>`, plan, usage).

## Proposed outcome

With a flag on, each Job gets short-lived S3 credentials that can only read and
write that task's own key prefixes. No long-lived key reaches the Job env. With
the flag off (default) nothing changes.

## Affected users and systems

`build_backend` (build Job dispatch), `spec_job_backend` (spec Job dispatch),
the MinIO deployment in factory-gitops (a non-root STS caller user).

## Constraints

- No new long-lived credential in a Job. The control plane gets one narrower,
  non-root MinIO user; the root key stops being the one it dispatches with.
- Default off: enabling needs the owner to create that user's secret.
- `core/artifact_store.py` is a byte-checked copy of the Factory hub file: not edited.
- Fail closed: with the flag on and STS failing, the dispatch fails; it never
  falls back to the root key.

## Open questions

None. Out of scope: gate-runner Jobs (separate dispatch path), making a Job's
writes to its own fetch-back keys untrusted (the control plane already validates them).
