# Intent: MCP status, logs and running list must reflect a kubejob build

## Problem

For a ~35 min kubejob build, `task_status` returned `phase: null, message: null`, `agent_status` returned `backlog` with no progress, `task_get_logs` returned `logs: [], total: 0` and `task_running` returned count 0. Cause: the REST routes the MCP proxy delegates to are thin. `GET /api/tasks/{id}/status` returns only `is_running`; `GET /api/tasks/running` lists only in-pod subprocess builds; `GET /api/tasks/{id}/logs` reads `task_logs.json` and legacy files, which a packed Job build never leaves on the control plane. Also (#2143) a task created and started sat in `backlog` for ~7 min with no Job and no visible queue state.

## Proposed outcome

An MCP poller can tell queued, starting, planning, coding, qa_review and complete apart, sees subtask progress, sees recent logs, and sees the task in `task_running`, for kubejob and subprocess builds alike.

## Affected users and systems

`apps/web-server/server/routes/execution.py` (`/running`, `/status`), `routes/tasks_logs.py`, `mcp_stdio/router.py`, `services/build_log_stream.py`, `agents/tools_pkg/tools/task_control.py` (`agent_status`). Portal and CFactory read the same routes and only gain fields.

## Constraints

Additive responses only (existing keys keep their meaning). Read-only. Logs are best-effort: a cluster read failure returns the existing result, never an error.

## Open questions

None. Decision (owner delegation 2026-11-18): derive from the same source as the portal (`task_to_dict().executionProgress`, the durable job-state row, the Job pod log tail), at the REST layer so portal and MCP agree; no new MCP-only code path.
