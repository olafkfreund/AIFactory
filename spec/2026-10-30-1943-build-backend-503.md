# Spec: 503 with the reason when the build backend refuses a launch

## Design

- `server/error_ref.py`: `async def build_backend_unavailable(request, exc) -> JSONResponse`
  returning `503` with `{"detail": str(exc)}`. The text is written by
  `agent_kubejob`/`agent_spec_creation` ("Builds refused: ..." /
  "Spec creation refused: ..."), from `backend_config_error`.
- `server/main.py` `create_app`: `app.add_exception_handler(BuildBackendUnavailableError, build_backend_unavailable)`.
- The handler only sees the error if it leaves the route, so each launching
  `try` gets `except BuildBackendUnavailableError: raise` ahead of its generic
  `except Exception`: `routes/execution.py` spec creation (~600), delegation
  (~791), start (~827), create-and-run (~1272), trusted-plan build (~1518);
  `routes/from_issue.py` (~613).
- Not `execution.py` ~1450: that `try` writes the trusted-contract record and
  never launches a build.

## Alternatives rejected

- Per-route `HTTPException(503, ...)` in each `except`: six copies of the
  status and message mapping instead of one.
- Teaching `client_error` the type: it returns text and cannot set the status.

## Risks

None beyond the status change; clients that retried on 500 also retry on 503.

## Verification

`tests/test_build_backend_503.py`: `create_and_run_task` with a stub
`start_spec_creation` raising the error lets it propagate (not a 500
`HTTPException`); a minimal FastAPI app with the handler and a route raising
it returns 503 with the reason; `create_app()` registers the handler.
