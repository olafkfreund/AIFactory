# Spec: PR review and clarification as Jobs (A4, #1932)

## Design

New module `apps/web-server/server/services/agent_job_backend.py`, reusing `SpecJobProcess`, `KubeJobLogStreamer` and the manifest/credential helpers from `spec_job_backend.py` and `build_backend.py`.

- Flag: `review_kubejob_enabled()` reads `AIFACTORY_REVIEW_BACKEND` (`subprocess` default, `kubejob`; anything else raises `BuildBackendUnavailableError`). It also requires the artifact store (DATABASE_URL), like spec creation.
- Shared `build_agent_job_manifest(job_id, argv, workspace_uri, extra_env, models)` built on `build_job_manifest`/`JobSpec` exactly as `build_spec_job_manifest` does (no service-account token, own namespace, 7200s -> 1800s deadline for these).
- PR review: `dispatch_pr_review(project_path, pr_number, followup, ...)` packs a local clone of the project (same `_prepare_spec_workspace` clone-and-pack, symlink checks kept, no `.aifactory` control files copied), runs `runner.py --project /work review-pr N` (or `followup-review-pr`). The runner, at the end, calls new `maybe_push_pr_review(pr_number)` (in `core/workspace_fetch.py`, keyed by the Job's fetch id from env `AIFACTORY_REVIEW_FETCH_ID`) which uploads only `.aifactory/github/pr/review_{N}.json`. On Job success the control plane runs `fetch_pr_review`: size cap 8 MiB, must parse as a JSON object, written atomically (0644) to the project's `.aifactory/github/pr/review_{N}.json`; anything else is a failed Job. The result is a `SpecJobProcess` whose `finish` does the fetch, so `PRReviewService._process_output` and `cancel_review` work unchanged (terminate/kill delete the Job).
- Clarification: `dispatch_clarification(prompt, oauth_token)` runs `claude --print --model haiku <prompt>` as a Job with no workspace; output is the Job log. The service reads `proc.stdout` up to a 256 KiB cap, `await proc.wait()`, and parses with the existing `_parse_clarification_json`; timeout (60s) calls `proc.terminate()`. Any failure returns the existing safe default.
- Wiring: `PRReviewService.start_review` and `generate_clarification_questions` branch on the flag; with it off the code path is byte-identical to today.
- Credentials: the Job gets the same env as a spec Job (OAuth token via `build_job_env`); PR review keeps `GITHUB_TOKEN` (it must read the PR) while clarification drops it. The control plane's `.token`/JWT/DATABASE_URL are never in the Job env (existing `build_job_env` allowlist).

### Revisions after Codex review (2026-11-17)

- Unpack: \`runner.py\` calls \`maybe_unpack_workspace(args.project)\` before any repo or config access (as \`spec_runner.py\` does), so \`/work\` holds the packed clone.
- S3 scope: review Jobs run \`scope_job_s3\` after every env merge for the workspace and fetch ids (same as spec Jobs). The clarification Job has no workspace, so its env carries no \`S3_*\` and no \`GITHUB_TOKEN\`.
- Clarification transport: the \`SpecJobProcess.stdout\` channel truncates lines at 16000 chars and drops past 1 MiB. The service reads at most 64 KiB and treats any truncation or parse failure as the safe default (skip=True); a truncated JSON object cannot parse, so this fails closed and never corrupts.
- Fetch destination: \`fetch_pr_review\` refuses if \`.aifactory\`, \`.aifactory/github\` or \`.aifactory/github/pr\` is a symlink, and requires the resolved destination to stay inside the project; the upload side skips a symlinked source.
- Cancellation: terminate/kill set the stop event; deletion is asynchronous and best-effort (as for spec Jobs). The Job's \`activeDeadlineSeconds\` (1800) bounds a failed delete. Clarification terminates on timeout, on overflow and in a \`finally\`, then awaits \`proc.wait()\` with a 5s bound. Tests cover timeout and cancel.
- Prerequisites: dispatch requires \`backend_config_error\` clear (DATABASE_URL) AND a constructible \`ArtifactStore\` plus successful packing and scoping; any failure refuses the review with an error event and never falls back to the in-pod subprocess.

## Alternatives rejected

- Separate Process adapter: duplicates 200 lines of polling and log streaming already tested.
- Return review output through logs only: the result file is large structured JSON; logs are lossy and capped.
- Fetch the whole `.aifactory/github/pr` dir: a Job could write other control files; allowlist of one file name is the point.

## Risks

GitHub token inside the Job is attacker-influenced context; the Job is isolated from the control plane but can use that token (same exposure as build Jobs today). Review Jobs cost cluster resources. Flag off by default, so no prod impact until flipped.

## Verification

Unit tests: flag parsing; manifest has no service-account token and the right argv; `fetch_pr_review` accepts a valid object, rejects oversize, non-object, symlink and missing; clarification parse through a fake `SpecJobProcess`; flag-off path unchanged (existing tests). `pytest` on touched test files, ruff check/format. Live check is an owner step after release (set the flag in factory-gitops, run one review).
