# Spec: clear the `ci-green` gate from measured host CI

## Design

The gate is cleared in AIFactory, from the CI signal AIFactory already measures (open question
1). The change is limited to `apps/web-server/server/services/pr_endgame.py` and adds one constant.

```python
# The one RFC-0013 system gate AIFactory measures itself: the host CI roll-up.
CI_GREEN_GATE = "ci-green"
```

### 1. `merge_disposition` (`pr_endgame.py`, defined ~line 670, `decide_merge` call ~line 778)

Today the call ends with:

```python
decide_merge(str(effective), **merge_gate_signals(spec_dir, fetched=fetched),
             deployment=deployment, satisfied_gates=list(satisfied_gates))
```

It becomes:

```python
signals = merge_gate_signals(spec_dir, fetched=fetched)
# Only the measured signal clears ci-green, never a caller-supplied name (any spelling).
gates = {g for g in satisfied_gates if str(g).strip().lower() != CI_GREEN_GATE}
if signals["host_ci_green"] is True:
    gates.add(CI_GREEN_GATE)
decide_merge(str(effective), **signals, deployment=deployment, satisfied_gates=sorted(gates))
```

- `ci-green` is added from `merge_gate_signals(...)["host_ci_green"]`. That value starts from
  `fetch_signals()`, is `True` only when the fetched value is literally `True`, and recorded
  metadata can only turn it `False`. So a contract, `task_metadata.json` or anything else the
  agent writes can never clear the gate (#1663, #1672).
- A caller-supplied `ci-green` in any spelling is dropped, so red or unknown CI always keeps the
  gate outstanding (`hold-blocking`, not `hold-async`).
- Nothing else is added. The docstring line "Gate evidence comes only from the caller" gains
  "or, for `ci-green` only, from the measured host CI signal". `human-approval`, `security-scan`, `sbom`, `dr-signoff` and unknown names
  are subtracted only when the caller passes them, as today.
- `risk_class: high` and `production_classification: production` don't depend on
  `satisfied_gates` and still hold.
- With no `fetch_signals`, or a task whose contract is unreadable, `host_ci_green` stays `False`
  and the gate stays outstanding.
- PR open (`_prospective`, ~line 2405) passes `host_ci_green: True`, so `ci-green` counts as
  satisfied there. That only arms the watcher (open question 2). The merge-time call (~line 2178)
  fetches real CI for the head SHA (`host_ci_green` plus the base branch's required checks), and
  GitHub merges with `--match-head-commit` on that SHA.
- `_clears_with_human_approval` calls `merge_disposition` with `HUMAN_ONLY_GATES`, so for a
  direct call a contract declaring `["ci-green", "human-approval"]` clears once both the approval
  and CI are green. On the live legacy path, `human-approval` still floors the tier to `blocking`
  before the PR opens (section 2), and that floor still holds. This change does not alter that
  case, and neither does a `reviewTier: blocking` already persisted on an older task.

### 2. `apply_path_risk_floor` (`pr_endgame.py` ~line 312)

```python
if state == "hold" or deployment_block_reasons(deployment):
```

becomes

```python
# ci-green is checked against measured CI at merge time; no CI exists yet (#2248).
if state == "hold" or deployment_block_reasons(deployment, satisfied_gates=(CI_GREEN_GATE,)):
```

This answers open question 3. The diff-based `floor_from_paths`, `state == "hold"`, high-risk and
production blocks, and every other required gate still floor the tier.

### Tests (`apps/web-server/tests/test_pr_endgame_merge_gate.py`)

These use the existing `_contracted`, `_deployment`, `_PASS` and `_spec` helpers.

1. `system_gates: ["ci-green"]` with `fetch_signals=lambda: _PASS` gives `AUTO_MERGE_DISPOSITION`.
2. The same contract gives `HOLD_BLOCKING_DISPOSITION` when fetched `host_ci_green` is `False` or
   `None`, or when there is no `fetch_signals`, even with metadata claiming `hostCiGreen: true`.
   It also holds with `satisfied_gates=["ci-green"]` or `[" CI-Green "]` and red or unknown CI.
3. A recorded `hostCiGreen: false` in metadata beats a fetched `True` and holds. The fixture is
   built with `_spec` directly, because `_contracted` already passes `hostCiGreen` from `_GREEN`.
4. `["ci-green", "security-scan"]` still holds with green CI.
5. Direct `merge_disposition` with `["ci-green", "human-approval"]`: green CI alone holds, and
   green CI plus `satisfied_gates=["human-approval"]` merges.
6. `production_classification: production` plus `["ci-green"]` still holds with green CI.
7. `apply_path_risk_floor` with enforcement on (set after `_contracted`, which clears it) and the
   diff stubbed to a harmless path. `["ci-green"]` alone returns `("auto", None)`, and
   `["ci-green", "human-approval"]` returns `("blocking", "blocking")`. The existing
   `test_an_outstanding_gate_still_floors_the_tier` stays unchanged.
8. Watcher handoff: extend the existing watcher regression (~line 692) with a `["ci-green"]`
   contract. The watcher arms, and `merge_pr` is called with the measured SHA only when the host
   roll-up and the required checks are both green. Unknown CI, or a red required check under a
   green roll-up, makes no merge call.
9. PR open through `run_pr_endgame`: a `["ci-green"]` contract with `autoMerge` on opens the PR
   with `auto_merge=True`.

## Alternatives rejected

- **PFactory stops emitting `ci-green`.** Already-signed contracts would stay blocked, and the
  explicit CI requirement would disappear from the audit trail. It also leaves AIFactory unable to
  clear any measurable gate.
- **Drop `ci-green` inside `deployment_block_reasons`.** The policy module can't tell whether CI
  was measured. The gate would also vanish from callers that do pass evidence.
- **Add a generic "measured gates" registry** (`security-scan`, `sbom`). Nothing measures those
  today, so this would be speculative.

## Risks

- **A wrongly green CI signal merges a held PR.** The signal is the one the low-tier rule already
  trusts, so this adds no new trust. Head binding (`--match-head-commit`) is unchanged.
- **Broader effect.** Every PFactory-planned task in a CI repo can now auto-merge when its tier and
  gates allow. That is the intended behaviour, and it only applies where `autoMerge` is on.
- **Host.** Prod AIFactory only, deployed through the normal release (3.21.15) and ArgoCD.
